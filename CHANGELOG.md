## [Não lançado]

### Segurança

- Chart `keycloak-replica` sobe a imagem composta `ghcr.io/unifesspa-edu-br/uniplus-keycloak` de `26.6.1-0` para **`26.6.4-0`** (Keycloak 26.6.4 + JAR `cpf-matcher`). O Keycloak 26.6.4 corrige 8 CVEs — incluindo CVE-2026-11800 (authentication bypass via JWT algorithm confusion), CVE-2026-9099 (privilege escalation group-admin → realm-admin) e CVE-2026-9799/9800 (authorization bypass) — além do bug de migração Postgres `keycloak/keycloak#48438` (restart loop ao migrar schema 26.5→26.6). `appVersion` e `version` do Chart (0.3.0 → 0.3.1) sincronizadas. Imagem publicada em `unifesspa-edu-br/uniplus-keycloak-providers#16`. Issue #392.

Anexado via `data.oci_core_private_ips` ao primary VNIC do k8s-host. IP `164.152.53.29` (já era RESERVED no recurso vivo — operação manual passada promoveu o ephemeral). Sobrevive a `tofu destroy && tofu apply` — recriar a VM mantém o mesmo IP, evitando reconfigurar DNS, gov.br callback URL, certs Let's Encrypt e `KC_HOSTNAME`. Custo: $0/h enquanto attached a VM running. Parte da Story #56 da Feature #43.
- `scripts/sync-tofu-outputs.sh` (novo) é a bridge entre `tofu output` (provisioning/oci/standalone) e os charts Helm consumidos via ArgoCD. Modos: tabela (default — lista outputs + mapeamento para campos do `environments/standalone/values.yaml`), `--diff` (verifica se IPs/FQDN do Tofu estão sincronizados com o values.yaml; sinaliza drift cedo), `--apply-configmap` (cria/patcha `ConfigMap` K8s `standalone-tofu-outputs` no namespace `uniplus` com todos os outputs como chaves planas — charts consomem via `envFrom`/`valueFrom`, útil para Story #57 quando KMS auto-unseal destravar), `--json`. Estratégia documentada no README do diretório `provisioning/oci/standalone`: schema do `values.yaml` continua provider-agnostic (em git, ArgoCD-readable); valores OCI-specific ficam hardcoded com `--diff` detectando drift; outputs sensíveis ou OCID-only não entram em `values.yaml`, ficam no ConfigMap. Story #58 da Feature #43.
- `provisioning/oci/standalone/dns.tf` codifica em OpenTofu os 11 DNS records do subdomínio `*.standalone.portaluni.com.br` na zona OCI DNS `portaluni.com.br` (`oci_dns_rrset.standalone_apex` apontando para o Reserved Public IP + `oci_dns_rrset.standalone_cname` com `for_each` cobrindo `api-ingresso`, `api-portal`, `api-selecao`, `ingresso`, `kafka-ui`, `minio`, `portal`, `redis-ui`, `schema-registry`, `selecao` apontando para o apex). ### Corrigido

- `description` do client `grafana` em `apps/keycloak-replica/files/uniplus-realm.json` encurtada de 362 para 227 caracteres. Mesma causa raiz do #196 (`CLIENT.DESCRIPTION` do Keycloak é `VARCHAR(255)`) — o client `grafana` foi adicionado depois daquele fix (SSO do Grafana) e não passou pelo mesmo audit. Diferente do #196 (que só quebrava no `UPDATE` via `keycloak-config-cli`), aqui o `--import-realm` já falhava no `INSERT` inicial — o pod do Keycloak entrava em `CrashLoopBackOff` na primeira subida, antes do Job `realm-reconcile` sequer rodar. A versão encurtada também remove o placeholder `${GRAFANA_CLIENT_SECRET}` do texto: como o Job `realm-reconcile` roda com `IMPORT_VARSUBSTITUTION_ENABLED=true` (substituição recursiva em qualquer campo do JSON, não só em `secret`), manter o placeholder na `description` faria o valor real do secret ser persistido em texto plano nesse campo, exposto a qualquer usuário com acesso de leitura aos metadados do client. Validado com reimport limpo (delete do realm via Admin API + restart do pod) contra Postgres 18 + PostGIS 3.6 e imagem `ghcr.io/unifesspa-edu-br/uniplus-keycloak:26.6.4-0`: `Realm 'uniplus' imported` / `Import finished successfully`; `description` persistida conferida via Admin API. Issue #394.
- Chart `clamav-scanner` ganha emptyDir mountado em `/var/lock` no container `clamd`. O entrypoint da imagem oficial cria `/var/lock/lock` (lockfile compartilhado) — `/var/lock` no FS image é `root:root` e o container roda como uid 100 → `Permission denied`. Cobre o último gap de paths writable que faltava (`/tmp`, `/run/clamav`, `/var/log/clamav` já tinham emptyDir). Issue #202.
- Chart `clamav-scanner` ganha `initContainer` `chown-signatures` rodando como root (`runAsUser: 0`, capability `CHOWN` only) que faz `chown -R 100:100 /var/lib/clamav` antes do container principal subir. O fix anterior (`fsGroupChangePolicy: Always` em #198) ficou ineficaz: o kubelet pula `fsGroup` operations para volumes hostPath-based por design — e o standalone usa StorageClass `standalone-local-nvme` (provisioner `rancher.io/local-path`, hostPath) — então o ownership do PV permanecia `0:0`, e o entrypoint da imagem oficial ainda crashava com `Operation not permitted` ao tentar chown como uid 100. Pod entra `Running 1/1` agora. Issue #200.
- Os 6 clients OIDC do realm `uniplus` (`uniplus-portal`, `kafka-ui`, `apicurio-registry`, `uniplus-api-{portal,selecao,ingresso}`) ganham o scope `basic` em `defaultClientScopes`. A partir do Keycloak 25, o claim `sub` no access_token foi movido do código built-in para o protocolMapper `oidc-sub-mapper` que vive dentro do client scope `basic`. Como os 6 clients declaravam `defaultClientScopes` explicitamente (sem incluir `basic`), o JSON sobrescrevia o default do realm e os tokens emitidos vinham sem `sub` — o `/api/auth/me` das APIs Uni+ retornava `userId: null` (descoberto durante smoke #191). Issue #187.
- Chart `clamav-scanner` ganha `fsGroupChangePolicy: Always` no `podSecurityContext`. Sem isso, em ambientes com k3s `local-path` provisioner (standalone), o `fsGroup: 100` declarado não era aplicado ao volume montado em `/var/lib/clamav` — o entrypoint da imagem oficial `clamav/clamav:1.4` tentava `chown` antes de fazer drop privileges para uid 100 e falhava com `Operation not permitted` sob `runAsNonRoot: true`, deixando o pod em `CrashLoopBackOff` desde o merge do PR #182. Issue #188.
- `description` dos 5 clients OIDC em `apps/keycloak-replica/files/uniplus-realm.json` (kafka-ui, apicurio-registry, uniplus-api-portal/selecao/ingresso) encurtada para ≤ 255 chars cada. Causa raiz: o schema da tabela `CLIENT` do Keycloak define `DESCRIPTION` como `VARCHAR(255)` desde KC 1.x; `--import-realm` trunca silenciosamente no INSERT inicial, mas `PUT /admin/realms/{r}/clients/{id}` (UPDATE via admin API — usado pelo `keycloak-config-cli`) rejeita com PG `22001 (value too long for type character varying(255))` → reconciliação falha em HTTP 500. Detalhes operacionais longos (procedure `kcadm.sh` para recuperar `client_secret`, semântica dos mappers) movidos para `RUNBOOKS.md`. Issue #196.
- `NetworkPolicy` do chart `keycloak-replica` ganha 3ª regra de ingress permitindo pods com label `uniplus.io/job-role=realm-reconcile` (mesmo namespace) chamarem o KC na porta HTTP. Sem isso, o Job `realm-reconcile` (ADR-010) — embora rodando vizinho ao KC — não conseguia alcançar o Service e morria em timeout/`backoffLimit`. Bug pré-existente do PR #183, mascarado anteriormente pelo `ImagePullBackOff` da issue #192. Escopo cirúrgico (label específica, não abre ingress geral do namespace). Issue #194.
- Tag de `quay.io/adorsys/keycloak-config-cli` em `apps/keycloak-replica/values.yaml` corrigida de `6.4.0-26.0.6` (inexistente — typo histórico do PR #183) para `6.5.0-26.5.4` (mais recente publicada; mesma major do KC vivo, admin API estável). Sem essa correção o Job `realm-reconcile` (ADR-010) ficava em `ImagePullBackOff` indefinidamente, bloqueando reconciliação automática do realm em re-deploy. Issue #192.
- Keycloak client `uniplus-portal` (public + PKCE, frontend Angular) recebe `protocolMapper` `audience-uniplus` (`oidc-audience-mapper` com `included.custom.audience=uniplus`, projetado apenas no access_token). Sem o mapper o token vinha com `aud: ["account"]` e as APIs Uni+ — que validam `Auth__Audience=uniplus` — respondiam 401 a qualquer chamada do frontend. Mitigação manual via `kcadm.sh` foi aplicada durante o smoke #166; agora o mapper está persistido em `apps/keycloak-replica/files/uniplus-realm.json` e o Job `realm-reconcile` (ADR-010, post-install/post-upgrade) o reaplica em re-deploy. Issue #186.

- Script `scripts/resize-standalone-oci.sh` que muda os shapes OCPU + RAM das 2 VMs OCI do standalone via OCI CLI (`compute instance update --shape-config`). Perfil `poc` (default) aplica `2 OCPU / 12 GB` no k8s-host e `1 OCPU / 4 GB` no data-host — economia de ~$215/mês (75%) sobre o shape original `4 OCPU / 32 GB` em ambos. Perfil `hml` para load real. **Operação reboota as VMs** (~30-90s downtime cada — `compute instance update --shape-config` é Reshape no OCI, não live resize); script pede confirmação interativa por padrão (flag `--yes` para CI). Stateful services (Postgres/Kafka/Redis/MinIO/Vault) e pods K8s religam graciosamente via systemd e auto-recovery do k3s — validado em uso real (10/05). Footprint dimensionado a partir de medição de uso real (k8s-host 9 GB / data-host 2.1 GB) com margem de 25-100%.
